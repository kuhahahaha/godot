# FR／PLAN 契约

## 文件与状态

`FR_<topic>.md` 写需求，`FR_<topic>_PLAN.md` 写实施计划，标准 Markdown 相互链接。大功能使用一份 OVERVIEW 维护依赖/唯一责任/状态，按职责拆分。输出到用户指定主本；未指定时在当前仓库 `docs/`。不创建只填标题的计划充数。

FR包含问题与现状、使用者/API表面（没有作者DSL时明确N/A）、行为要求、边界、验收以及与相邻能力关系。PLAN使用下面章节，细节按改动规模展开，标题保留以便机械检查：

1. `## 0. Decisions`：范围、API/类型/字段/默认值、状态转换与合法操作、线程/资源权威、错误及恢复、依赖与不含项。技术选择应具体；需要运行才能定案的前提设置带分叉结果的验证关口，不能声称已证明。
2. `## Sources`：源版本、完整可定位路径＋符号＋相关行、核到的行为。源码结论、推断、计划与运行证据分列。来源引用用 `[说明](绝对或相对路径:行号)`；新文件在清单中以代码路径列为新增，不虚构源码链接。
3. `## Implementation`：按可验证阶段列数据流、调用链、注册/桥接、资源申请/换绑/失败/退休、命令与反馈；每阶段 `Success check`。未来新增的API要完整签名/字段语义和错误行为，不能借代码形状假装已有API。
4. `## Tests`：先分支矩阵，列 `ID / Trigger / Expected / Test / command / RED` 信息，可将Test与command合列。ID用T01等。覆盖合法/非法状态、边界、所有错误、缺省/显式值、顺序/邻居组合、失败后恢复与清理；顺序不定则比较集合/不变量。按适用性列，不能把不涉及的DSL或渲染能力硬塞进计划。
5. `## Example Impact`：公开行为变化；受影响Godot类/API/示例/文档；每项 update、reviewed-no-change或not-applicable及依据；专项与周期全量回归区分。内部后端可以没有作者示例，但仍需测试宿主与相邻消费者。
6. `## Build and acceptance`：实际可用构建/运行入口、目标/driver/config、二进制身份、匹配用例数量、分层通过标准、必需平台与未测平台。不能把SKIP、缺设备、无匹配测试、部分套件或已知泄漏当全通过。
7. `## File-change checklist`：逐文件新增/修改/只读和职责，覆盖SCons、注册、class XML/绑定适用性、测试发现、夹具、帮助/文档；不涉及的层明确原因。
8. `## Review`：机械检查命令/结果、独立审查文件/版本、逐项处理、仍未决事项。
9. `## Self-review`：六项保证对应具体章节或证据；不能仅填勾号。

## Godot集成核查

- 直接编辑 `servers/`、新增 `modules/`、Scene Resource/Node、RenderingServer API 是不同入口：追到对应 SCsub、注册/初始化/销毁路径及所有实现类，不预设自动glob或中央表。
- 公共接口新增核查 RD、Compatibility、dummy 等实现和 unsupported 行为。必要的安全拒绝/诊断不等于实现全后端，不得静默CPU降级。
- 共享绘制/存储修改须列受影响旧消费者；普通材质、阴影、多视图、历史不是一个“能显示”断言。
- 涉及资源，分别说明CPU对象、RID、内容版本、在途命令、GPU完成、回调和场景引用。线程与ownership证明不能由“调用free”代替。
- 复用已有缓存、排序、资源导入、注册和测试机制；同样功能如不复用，写明真实限制。不得为单个特效建立另一个通用引擎。

## 计划的证据边界

来源可核实并不代表方案已实跑。独立审查可通过一个明确的风险探针计划，而不是替探针给出肯定结果。探针失败后的路径须具体到受影响契约/FR及停止的实施部分；可继续的无关规划不停止。

正式产品语义未定不伪装技术细节：记录选项、影响和推荐，保持needs-decision。已明确的用户范围不能因测试困难被删掉。临时运行目录或日志只做证据，不作为长期唯一接口定义。
