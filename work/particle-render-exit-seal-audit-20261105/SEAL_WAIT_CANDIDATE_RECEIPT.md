# Metal ordinary-frame seal candidate — 2026-11-04

Status: source-matched Godot candidate verified with visible Metal World/System/Cancel; separate Direct/per-ticket product audit remains open. This is not a six-link acceptance.

## Root cause

The same-pair `metal-prepare-world.log` has `MTL_PREPARE branch=copy_commit serial=154 issued=1 observers=1` immediately before `Failed to seal the rendering frame`. The Metal copy queue had already committed and transferred an observer, but the nonblocking `qualification_prepare_segment()` intentionally returned `ERR_BUSY`. Ordinary `swap_buffers()` propagated it as a seal error, leaving the current frame unexecuted. The same serial later reached `completion_retired`; the log then crashed in Metal `presentDrawable`, which remains a separate unproven issue.

## Candidate

The prepare interface now takes a `p_nonblocking` flag. `_end_frame()` passes its existing mode. On the ordinary frame, Metal acquires the two queue locks normally, commits the original copy command once, waits for that exact command's completion handler, checks its status, then retires the original owner while preserving the Frame observer. Qualification maintenance retains try-lock, `ERR_BUSY`, and no-wait behavior. The Vulkan implementation retains its `OK` behavior. A new native Metal test checks that an ordinary preparation returns `OK` with one issued source, completed original bytes, one frame observer release, and a subsequent no-work preparation.
