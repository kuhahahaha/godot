## Chosen dataflow and scope

One E20 operation uses one existing original prepared QualificationTicket. That ticket owns (a) existing V1 checked buffer-upload plans, (b) exactly one typed image-transfer plan, (c) the issued image content ref and exact clear/transfer facts, (d) its existing capture/body/readback records and native facts, (e) the typed source/consumer receipt. Producer ticket and consumer ticket are deliberately the same original ticket in this narrow profile. Passing the ref to another ticket fails; another operation reuploads and transfers afresh. This supplies cross-frame exact-native-source completion without a second producer registry or retained-ticket cycle. Root must adopt the explicit distinction from T1's shorthand “producer ticket physical retirement”: the earlier producer PREFIX within this SAME not-yet-consumed ticket has exact completed native sources and original frame/staging returns; the whole ticket is not falsely labeled physically_retired until consumer/cancel finishes. If C05 insists on a separate wholly retired producer ticket instead of this stronger explicit prefix receipt, that is a scope revision, not a fact supplied by a missing graph edge.

The real source buffer, destination image and dynamic sampler are three distinct parts of the existing StorageOwner allocation. The source buffer is transfer scratch, not a second symbolic allocation/word role: the ONE original Ptexture symbolic allocation still maps to its actual texture+sampler children under C04's full original key/view. Reserve BOTH pair children and all failure/return slots before the first native effect, attach prefix to B's admitted slot first, and retain either creation order's known/possible prefix on failure/state2; publish no partial binding. Scratch uses that same owner/slot account and introduces no second source key. C asks D's scoped texture-layout query for canonical row pitch and source byte count, creates the real original source buffer, and byte-copies its captured 64-byte image into two 32-byte rows at that pitch with zeroed native padding. It passes the source 64-byte capture digest AND packed-upload digest through the exact typed plan / existing checked upload plans. No pixel bit is decoded/reencoded. C owns pixel semantics and its independent expected values. D does not declare arbitrary bytes to be semantically correct; it proves exactly which copied/digested original upload bytes reached which original image subresource and were admitted as the consumer's source.

The source/capture association is concrete and remains in its original domains: `FixedMethodInputSourceView` has a private constructor (`ANGE_w2/src/particle/gpu/gpu_templates.h:271`), `DefaultQualificationResources::select_fixed_source` checks its original registry and `owns_allocation` (`src/particle/di/di_qualification_resources.cpp:49`), `fixed_method_texture_image_bytes/write_fixed_method_texture_image:140/158` derive and write actual LE bytes, and `CaptureReceipt` retains the actual `InternalRecipeTemplateRef` (`src/particle/di/capture_receipt.h:26/43`) through B's original Store admitted capture cell. B/C must move that actual retained source/capture receipt into their pre-reserved original slot BEFORE preparing/uploading native work, joining its vector ordinal, original Ptexture full key/view, CPU source version, request_digest and original `parent_serial/reservation_serial`; D does not authenticate a C source owner from a caller-invented numeric token. No new C-owner serial or registry is proposed. D attaches the exact 64-byte capture association and verified digest to the already admitted original ticket/plan/content/native record. C05 joins its retained actual source/capture owner to this D-issued native association; copied labels alone grant neither source permission nor native version.

`TextureCaptureV2` is56 bytes: original CPU source_version, captured_byte_count=64, SHA256 of the exact 64 LE bytes, original vector ordinal, reserved0. Typed prepare checks its ordinal equals original UploadPrepare.base.vector_ordinal and byte count64, and B/C supplies source_version from the original capture shape (`TextureCaptureShape{1,64}` today), never from native backing/query. During the designated EXISTING checked `qualification_upload`, after copied payload SHA256 verification, D extracts exactly the two 32-byte pixel rows from canonical packed row offsets, hashes their concatenation and compares capture_digest, checking every native padding byte is zero. It stores both actual raw capture digest and actual packed-upload digest in the same original ticket. No float load, NaN canonicalization, verifier/oracle data or parameter buffer enters this raw-image digest. Native content_version starts0 and only the actual full transfer commits it; CPU source_version 1 can never set it. Fourteen occurrences retain their actual original per-occurrence keys/owners/ordinals; no ordinal-derived sampler role/key is manufactured.

The zero-payload sampler follows explicit typed Reserved→Creating→Live→Retiring→Released part state in the SAME owner even when all byte totals are0: actual native object/ref/serial, outstanding records/borrows and metadata/native child quotas determine drain. Legacy zero-byte BUFFER remains Released/no allocation as before. `borrow/observe/read_backing` accepts a known-live sampler by explicit kind and exact original owner/session/ref/serial, not nonzero bytes, and rejects state2/unknown. Its view has zero byte/texel range and content version0. No separate debt counter or payload1 workaround is proposed.


Destination texture uses the r1 owned root profile plus CAN_UPDATE_BIT (wire TRANSFER_TO bit4): exact wire usage=7, actual RD sampling|storage|can-update. No public texture_update is used. For these14 occurrences, enforce width=height=2 and image logical bytes64 in typed prepare (generic allocation V2 remains separately described). One full color mip0/layer0 transfer writes `[0,2)×[0,2)×{0}`; source is a real original E05 buffer and one original GPU `RecordedBufferToTextureCopy`. No compressed, 3D, partial-image, shared/imported, format conversion, async worker or multiple-mip profile is silently accepted.
