Root cause and compatibility:
Old RETURNED branch compared the offered budget with the immutable old budget.
Different live budget consumed and accepted again in the same call; different
expired budget discarded the old result and returned OK. Expired offered budget
with a live original PENDING/QUEUED control also returned misleading OK.
New nonzero RETURNED retry consumes exactly once and returns the actual old
native_error, regardless of offered budget, with no replacement admission.
New nonzero retry retires an original PENDING whose retained immutable budget
has expired to a proven no-effect result(OK), then consumes it. This uses the
same existing cell and RELEASE's never-published expiry precedent. No native
service, budget renewal, or physical completion is asserted.
A nonzero expired offer while the original PENDING budget is still live, or
while original QUEUED/EXECUTING, now returns ERR_BUSY instead of OK. This is the
intentional compatibility correction to the old ambiguous metadata behavior.
Zero budget queries preserve their existing behavior.

Exact public caller semantics:
1. Zero controls, receipts, passes, OR deadline means metadata query only. OK
   from this shape never establishes control consumption, even after expiry.
2. Nonzero live offer with no outstanding control can accept/schedule one new
   OBSERVE and returns Busy on normal asynchronous admission.
3. Nonzero retry of live original PENDING retains the original serial/budget.
   Only a currently live offer permits FIFO publication. Offered values never
   replace or recharge its immutable execution budget.
4. Original expired PENDING has never published: any nonzero retry consumes
   its no-effect return, preserving serial, without admission of a new turn.
5. QUEUED/EXECUTING is never synthesized as no-effect on deadline expiry. It
   remains Busy until real FIFO execution returns. A lookup/schedule race may
   conservatively return Busy for a turn which just returned; retry consumes.
6. RETURNED consumes only that old turn and returns its actual native_error.
   Busy can therefore mean either outstanding or consumed-with-Busy. Ordinary
   service calls alone do not expose this distinction. Never infer state from
   OBSERVE service_pending/service_control_serial, which remain RELEASE fields.
7. Strict drain-only protocol without any new ABI: offer valid DTO with all
   counts nonzero and an already-expired NONZERO deadline. Preserve every old
   diagnostic and repeat this expired offer until OK. Such an offer cannot
   accept any new turn. Busy may consume an old Busy result; the next expired
   call then returns OK with no cell outstanding. If original PENDING is live,
   it stays Busy until its own finite immutable deadline expires, then returns
   no-effect/consumed. Queued work must actually return. An expired nonzero OK
   now establishes no outstanding control at this call; it is NOT GPU, physical
   obligation, logical request completion, or runtime receipt evidence.
8. After that drain boundary, caller may invoke cancellation/release, or make
   a deliberately separate live service call if physical maintenance is still
   needed. Do not use a live offer as the drain-only confirmation: with an empty
   cell it may accept new work.
9. Existing restrictions remain: a different outstanding kind returns Busy;
   invalid owner/ref fails validation. A RETURNED output_generation.native_released
   still refuses public consumption with ERR_UNAVAILABLE because its full typed
   internal result must be consumed by the original capable owner. Public drain
   cannot replace that seam. Treat errors as diagnostics, never consumption proof.
